Background and motivation

We are migrating a mixed GCC/Clang platform. Some producers or consumers still use GCC. Clang LLVM bitcode is not GCC LTO IR. FatLTO was enabled to preserve a native representation in static objects/archives so GCC or no-LTO consumers can use that representation. A normally linked shared library/executable is machine code; dynamic use of a Clang-built shared library by a GCC-built program does not itself require GCC to read LLVM bitcode.

Global Options adds -ffat-lto-objects only when LTO is enabled. A clean no-LTO rebuild is distinct from reusing exactly the same fat object produced earlier. A whole-RPM LTO rebuild does not automatically rebuild external/vendor archives, eliminate per-target -fno-lto, convert assembly to IR, or qualify future native consumers of shipped static inputs.

Our current fallback operates on eligible IR during regular LTO for a PIC output. It adjusts inappropriate symbol-locality assumptions and direct-access-external-data handling before code generation, including a concern about accesses introduced by stack-protector codegen. Read the actual design for its precise conditions, including prevailing definitions/local aliases. It is not a rewrite of native instructions and is not a claim to undo arbitrary earlier optimization.

HQ's review concern

A Clang fat object compiled with -fno-pic contains non-PIC native code and an embedded .llvm.lto representation. When a compatible LTO consumer claims the embedded IR, the fallback can operate there. If the same bytes are consumed natively, the old machine code remains. The IR warning does not diagnose the native path. An LTO-only audit therefore does not qualify a native/no-LTO consumer.

We accept the missing validation scope and have investigated it. Proposed baseline to challenge

1. Keep existing regular-LTO fallback and package PIC repairs.
2. For identified user-space targets that must support shared-library consumers or export general PIC static inputs, generate the entire object with -fPIC before frontend/IR optimization. Both embedded IR and native code then follow a consistent PIC contract. A PIE application target is a separate contract; -fPIE is not a universal substitute for -fPIC static libraries.
3. Start with target-aware build configuration. If coverage requires compiler support, evaluate an explicit opt-in, reversible policy option applied early enough to coordinate frontend semantics, IR properties/locality and backend relocation model. No option name or patch point is approved. Do not silently override an explicit -fno-pic conflict: diagnose it until the policy is deliberately resolved. Avoid changing legitimate visibility or semantic-interposition requests.
4. Do not infer future shared output from -flto/fat alone. Keep Kernel/modules/firmware/bare-metal/CRT/special targets outside the user-space contract. The Customized MLGO model-comparison Base must not acquire this experimental PIC change.
5. Historical pure-native GCC/vendor inputs cannot be promised automatic repair. Rebuild from source with appropriate PIC, request a PIC variant, or reject the unsupported consumer. Better diagnostics/auditing can identify RPM, object/member SHA, relocations and actual consumer; that is protection, not successful binary repair.

Alternative worth reviewing: native-only PIC generation in FatLTO

LLVM's buildFatLTODefaultPipeline currently performs pre-link optimization, EmbedBitcodePass, cleanup, then additional optimization/native emission. This suggests a potential split but does not prove a post-embed PIC pass is sound. It may be too late to undo non-PIC assumptions.

Evaluate frontend __PIC__/__PIE__ conditionals, TLS model selection, dso_local/interposition assumptions, early optimization of address comparisons, direct-access-external-data, TargetMachine relocation model, late stack protector references, visibility/aliases/COMDAT, CFI/EH and inline assembly. Cloning already optimized IR may preserve irreversible assumptions. A second frontend invocation under PIC may change definitions, layouts and symbols relative to the embedded original IR, so simply combining two outputs may be unsound.

We currently prefer consistent PIC generation for both representations over preserving non-PIC IR and independently repairing native code, unless a sound narrower contract and useful benefit can be demonstrated. Please disagree if there is a better feasible design.

Other alternatives to assess briefly

- A separate PIC static variant for libraries whose non-PIC native variant must remain supported.
- Restricted native linker relaxation/rewriting. Distinguish a genuinely supported, provably safe pattern from a proposed universal non-PIC-to-PIC rewrite. Explain register allocation/instruction-layout/interposition/unwind implications.
- Extracting .llvm.lto and regenerating PIC at link time: this is an IR path, not native-only consumption. Consider incomplete coverage of inline/module assembly, ld -r combinations, archive symbol indexes and mixed objects. Do not suggest transparent substitution without a sound losslessness contract.
- -z notext, suppressing errors, forcing symbols local or hiding TEXTREL: these are not accepted general fixes.

Required acceptance criteria

Use checksum-pinned new objects in paired LLVM regular-LTO / GCC -fno-lto native / direct no-plugin GNU linker cases, shared and PIE, objects and archives, plus clean no-LTO rebuilds. Preserve old failing inputs as negative controls. Explicit policy conflicts should reject; do not call that a failed repair if rejection is the defined behavior. Prove actual consumption rather than inferring it from flags.

Request a staged matrix for ARM/Thumb, TLS/threads, external/internal data and pointer identity, executable overrides/copy relocs, weak/hidden/protected aliases and COMDAT, stack protector, C++/EH, archive extraction/whole-archive/thin archives, mixed assembly, partial linking and optimization levels. ThinLTO must be separately qualified or explicitly excluded. Include target isolation tests for Kernel/special builds, disabled-policy behavior and no-LTO builds. A targeted native relocation check must account for actual archive extraction, live sections, symbol binding/output type and architecture; do not reject every ABS relocation or debug-section relocation indiscriminately.

Production acceptance must follow actual producer/consumer dependencies and compare against explicit -fPIC controls. Record build failures separately from runtime regressions, and measure size/performance/stability rather than speculate. Do not present absence of warnings/TEXTREL as sufficient acceptance.
