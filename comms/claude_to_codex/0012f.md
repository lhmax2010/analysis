# 0012f • Claude (PM) → Codex: kernel trial for `-moutline` with MLGO

Date: 2026-11-24. This extends the kernel trial in 0012e §Scope 4. Run it in the same kernel build batch. Do not add a separate launch.

## Question to answer

Can the KantSU2E perf kernel (`tztv-kernel-perf`, ARM32, currently 100% A32) use the Machine Outliner (`-moutline`) together with the Official MLGO LLVM? How much does it save, and what does it break?

HQ (J. Chung) asked whether `-moutline` and MLGO can be used together. Our position is that they are independent passes: the ML inline advisor works in the IR inliner, the ML eviction advisor works in register allocation, and the Machine Outliner works on the final machine code after register allocation. **Prove or disprove this with builds.** Do not argue it.

## Prerequisites (from 0012c+d)

- The kernel source identity and the `.config` used by Official 37736448. If these are not proven, report this whole task as blocked, with the reason.
- **How MLGO is turned on in the Official LLVM.** Find out from the SRPM 9.1 vs 11.1 spec diff and from the clang config or default flags: is it a built-in default, a config file, or a `-mllvm` flag? Also determine whether the kernel's compile lines actually get it. Prove this with a `-mllvm` remark, a statistic, or a `-print-…` output from one kernel compilation unit. The difference in uImage size between Official and Customized is not enough proof.

## Lanes

All lanes use the same kernel source, the same `.config` and the same GBS root, Official Base/Product, and a dedicated empty local repo.

| Lane | Compiler flags | Purpose |
| --- | --- | --- |
| K0 | As shipped (MLGO as delivered) | Baseline; must reproduce the shipped `vmlinux`/uImage size |
| K1 | K0 + `-moutline` | The outliner with MLGO |
| K2 | K0 with MLGO off (use the documented switch from the prerequisite) | Isolates MLGO's own effect on the kernel |
| K3 | K2 + `-moutline` | The outliner without MLGO; with K0/K1/K2 this gives the 2×2 table |
| K4 | `CONFIG_THUMB2_KERNEL=y` (0012e) | Thumb-2 kernel |
| K5 | K4 + `-moutline` | Thumb-2 plus the outliner |

If the prerequisite shows that MLGO cannot be switched off for the kernel without changing the toolchain, drop K2 and K3 and state why.

**How to inject the flags.** Use a local trial edit of the kernel spec only, `make … KCFLAGS="-moutline"`. Store it as a patch in the repo. Do not submit anything to Gerrit or OBS. The ARM32 kernel has no Clang LTO, so the flag acts at compile time.

## Proof that the flag was delivered

- **Compile lines:** show `-moutline` (or `-mllvm -enable-machine-outliner`) on the compile lines with `V=1`, sampled from at least `kernel/sched/`, `mm/`, `net/core/` and `arch/arm/`.
- **Outliner ran:** report the count of `OUTLINED_FUNCTION_*` symbols in `vmlinux`. Zero means the outliner did not run, so the lane fails. The likely cause is that A-profile ARM needs the outliner forced on rather than left at the target default.

## Static results for each lane

1. **Sizes.** `vmlinux` `.text`, `.rodata`, `.init.text` and SHF_ALLOC totals; zImage/uImage size; total size of all `.ko` files.
   - Highlight the resident RAM delta in particular. Kernel text is not paged, so the `.text` saving counts directly as RAM saved.
2. **Outlined functions.** How many there are and their total bytes, and which subsystems they come from (`sched`, `mm`, `net`, `fs`, drivers, `arch/arm`).
3. **Section safety audit.** For every `OUTLINED_FUNCTION_*`, list the sections of its callers. Flag every case where:
   - an outlined function is called from `.noinstr.text`, `.head.text`, `.entry.text`, `.idmap.text`, `.hyp.text` or a `__kprobes` section;
   - the caller is in `__init`/`.init.text` but the outlined body is in resident `.text`.

   Report each flagged case and the caller function behind it.
4. **Unwind coverage.**
   - Check that every outlined function has a `.ARM.exidx` entry (`CONFIG_ARM_UNWIND`), or check frame-pointer consistency, whichever the config uses.
   - Report any outlined function with no unwind entry.
5. **Modules.** Do all external and vendor modules from the retained owners still build and load-link (`modpost`) against the K1/K5 kernels?
